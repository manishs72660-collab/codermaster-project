1. Project Overview

CodeMaster is a MERN-based online coding platform for students, college admins, and platform admins. It provides a complete ecosystem for practicing Data Structures & Algorithms (DSA), participating in timed coding contests and MCQ contests, engaging in real-time 1v1 duels, collaborating in community discussions, and communicating directly with admins via a live chat system.

1.1 Core Features

  • Practice Arena: 1000+ problems with tags (array, string, graph, DP), difficulty levels (Easy, Medium, Hard), and paginated search.
  • Async Code Execution: Judge0 CE sandboxed execution (C++, Java, Python, JavaScript) through BullMQ background workers. Submissions return 202 Accepted immediately and results are pushed over Socket.io.
  • Coding Contests: Timed events with multiple problems, private/public visibility, live leaderboards, and tab-switch violation tracking (3-strike disqualification).
  • MCQ Contests: Create/play timed quizzes with multiple-choice questions; automatic grading and rank calculation.
  • Real-time Duels (Battles): 1v1 challenges on random problems with ELO rating, live progress sharing, and spectator mode.
  • Admin Communication: Students can request a chat with an online admin; full message history.
  • Community Feed: User-generated posts, comments, and upvotes (similar to a mini-Reddit).
  • College Management: Platform admins can onboard colleges (via requests); each college gets its own admin(s) and scoped contests/leaderboards.
  • Video Solutions: Admins upload video explanations via Cloudinary integration.
  • AI Assistance: Gemini API integration for doubt solving (hints, code reviews, complexity analysis).

1.2 Feature Deep-Dive

🧩 Practice Arena

  • Browse 1000+ problems in a paginated list (?page=&limit=) with infinite scroll in the UI, then narrow by difficulty (Easy, Medium, Hard) and tags such as array, string, graph and DP.
  • Run executes your code on the visible test cases and returns the result right away. Submit runs the hidden test cases through the async queue.
  • Languages: C++, Java, Python and JavaScript. The editor is Monaco, the same engine as VS Code.

⚡ Async Code Execution

  • Submitting returns 202 Accepted in milliseconds. A BullMQ worker runs all hidden test cases in one Judge0 batch and pushes the verdict to your private Socket.io room.
  • If Judge0 fails, the job retries 3 times with exponential backoff and then lands in a dead-letter queue, so one outage does not lose submissions.
  • A 10-second per-user cooldown, enforced atomically in Redis, stops submission spam.

🏆 Coding Contests

  • Admins and college admins create timed contests with several problems. Public contests need a click on Register. Private contests need a join code.
  • Middleware gates every step: the contest must exist, have started, still be running for submissions, and you must be registered.
  • The live leaderboard counts the first accepted solution per problem, with the earliest submission breaking ties.
  • Anti-cheat: tab switches and minimizing are reported. Strike 1 is a warning, strike 2 a strict warning, and strike 3 disqualifies you and removes you from the board.

📝 MCQ Contests

  • Up to 20 questions, each with 4 options. The correct option is stored server-side and stripped from the questions endpoint.
  • You submit the whole answer sheet once. The server grades it, ranks everyone, and applies the same 3-strike rule.
  • After the contest, your graded sheet shows the correct answers and explanations.

⚔️ Real-time Duels

  • Create a room, share the room code, and the opponent joins. Both players get the same problem and a start signal at the same moment.
  • You see your opponent’s test-case progress live. Spectators join a separate room and watch the editors update.
  • The first correct submission wins. Ratings use ELO with K = 32, scaled by difficulty (Easy 0.75, Medium 1.0, Hard 1.5).
  • Afterwards you can request a rematch on a new random problem, or replay both players’ final code.

🎓 College Management

  • A college registers through a public request. The platform admin gets an email and can approve it (a temporary password is emailed to the requester) or reject it.
  • Each college has its own admin, scoped contests, a student list, and an internal leaderboard. College admins can promote students to admin.
  • Deleting a college cascades to its users, submissions and Redis keys.

💬 Admin Chat

  • Admins who are online are tracked in Redis. A student picks one and sends a request, the admin accepts or declines, and both join a private room.
  • Every message is saved, so the full history stays available after the chat ends.

📢 Community, Discussions and Solutions

  • The community feed supports posts with tags, sorting, upvotes and comments, in the style of a small forum.
  • Each problem has its own discussion thread with replies.
  • After you get an accepted submission, you can publish it as a solution post with your explanation.

🎥 Video Solutions

  • Admins request a signed upload URL, upload the video straight to Cloudinary, then save the metadata. Thumbnails are generated automatically.
  • Deleting a video also removes it from Cloudinary.

🤖 AI Doubt Solver

  • Gemini powers hints, code reviews and complexity analysis, so you can get unstuck without reading the full solution.

📊 User Profiles

  • A submission heatmap, skill breakdown, solved counts by difficulty, daily streak, and your global and college ranks.
  • Sign in with email or Google. Tokens rotate on refresh, and logout blacklists the token.

3.3 Async Submission Flow (BullMQ) ⭐

Unlike a traditional synchronous design (where the HTTP thread blocks 10–15 s on Judge0), CodeMaster decouples Judge0 execution into a background worker pipeline.

sequenceDiagram
    participant C as Client
    participant A as Express API
    participant Q as BullMQ (Redis)
    participant W as Worker
    participant J as Judge0 CE
    participant S as Socket.io

    C->>A: POST /code/submit/:id
    A->>A: Create Submission (status = pending)
    A->>Q: Enqueue job
    A-->>C: 202 Accepted { submissionId, status: "pending" }
    Q->>W: Worker pulls job (concurrency = 10)
    W->>J: Batch-run hidden test cases
    J-->>W: Results
    W->>W: Update Submission (accepted / wrong / error)
    W->>S: Emit to room user-{userId}
    S-->>C: submission_result

Why this matters

  • API latency drops from ~15 s to <200 ms: the endpoint no longer waits for Judge0.
  • Retry handling: BullMQ retries failed jobs up to 3 times with exponential backoff.
  • Dead-letter queue: permanently failed jobs are kept for inspection.
  • User isolation: one user's slow Judge0 request does not hold up HTTP threads for others.

Scope note: this pipeline is used for practice submissions (POST /code/submit/:id).

Key change: async submission flow

Old behavior (v1.0.0):

POST /submit → waits ~15 s for Judge0 → returns { accepted: true/false }

New behavior (v2.0.0):

POST /submit → returns immediately { submissionId, status: "pending" } (202)
        ↓
Worker processes Judge0 in the background
        ↓
Socket.io emits `submission_result` to room user-{userId}
        ↓
Frontend receives { accepted, passedTestCases, totalTestCases, runtime, memory }

Client example

// 1. Submit (fast)
const res = await axios.post(
  `/code/submit/${problemId}`,
  { code, language },
  { headers: { 'x-socket-id': socket.id } }
);
// → { submissionId: "...", status: "pending" }

// 2. Listen for the result
socket.on('submission_result', (data) => {
  // → { accepted: true, passedTestCases: 10, totalTestCases: 10, runtime, memory }
});

7. Real-time Architecture (Socket.io)

The Socket.io server is initialized in src/index.js and wired to src/socket/index.js. It uses the same Redis infrastructure to track online users/admins, and the Redis Adapter to broadcast across instances.

7.1 Connection & Authentication Flow

  1. Client connects (handshake).
  2. After authentication (Redux isAuthenticated), the client emits user:online with { userId, role }.
  3. The client also emits join_user_room, which places the socket in the private room user-{userId} (used for submission results) ⭐.
  4. Backend stores the mapping in Redis (online_users hash) and adds admin IDs to the online_admins set.
  5. On disconnect, cleanup removes the entries.

7.3 Horizontal Scaling via Redis Adapter ⭐

To run multiple Node.js instances behind a load balancer, the Socket.io server uses @socket.io/redis-adapter.

Configuration (src/index.js):

const { createAdapter } = require("@socket.io/redis-adapter");

const pubClient = client.duplicate();
const subClient = client.duplicate();

Promise.all([pubClient.connect(), subClient.connect()]).then(() => {
  io.adapter(createAdapter(pubClient, subClient));
});

How it works

  1. A message emitted on Server A is published to a Redis channel.
  2. Server B (subscribed to the same channel) receives it.
  3. Server B forwards it to its own local sockets.

What this gives you

  • ✅ Duels, contests and chat work when the two players are connected to different servers.
  • ✅ Worker-emitted results reach the user regardless of which instance holds their socket.
  • ✅ No cross-instance state kept in process memory.
  • ⚠️ Redis Pub/Sub is fire-and-forget: if an instance is briefly disconnected from Redis, events published in that window are not replayed. Clients should fall back to fetching state over REST (for example GET /code/solveproblem/:id) on reconnect.

Per-user rooms The join_user_room event places every user in a user-{userId} room. Workers emit to this room, so users get results regardless of which instance served their HTTP request.

8. Rate Limiting Strategy ⭐

CodeMaster uses atomic Redis Lua scripts for rate limiting. Multi-command approaches (ZADD + ZCARD + EXPIRE issued separately) leave a race window where concurrent requests can slip past the limit. A Lua script executes as a single atomic unit inside Redis, so the check and the increment cannot interleave with other requests.

8.1 Global IP-Based Limiter (Sliding Window)

  • Files: middleware/ratelimitor.js + middleware/rateLimiter.lua
  • Window: 1 hour (3600 seconds)
  • Limit: 100 requests per IP per hour
  • Applied to: /auth/register, /auth/login (brute-force protection)
-- rateLimiter.lua (atomic)
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local max_requests = tonumber(ARGV[3])
local unique_id = ARGV[4]

redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local current = redis.call('ZCARD', key)

if current >= max_requests then
    return 0  -- BLOCKED
end

redis.call('ZADD', key, now, unique_id)
redis.call('EXPIRE', key, window)
return 1  -- ALLOWED

// Node.js caller (single Redis round-trip)
const isAllowed = await redisClient.eval(rateLimiterLua, {
  keys: [key],
  arguments: [currentTime, windowSize, MaxRequest, uniqueId],
});
Before After
Redis round-trips per request 3–4 separate commands 1 (EVAL)

  • File: middleware/submitrate.js
  • Window: 10 seconds per user
  • Limit: 1 request per user per 10 s
  • Applied to: /code/submit/:id, /code/runcode/:id
const isSet = await client.set(redisKey, "cooldown_active", {

9. Security Architecture

9.1 Authentication (JWT + Cookies)

  • Access Token: JWT signed with JWT_KEY, expires in 1 hour. Stored in an HTTP-only cookie (accessToken).
  • Refresh Token: JWT signed with JWT_REFRESH_KEY, expires in 7 days. Stored in an HTTP-only cookie (refreshToken).
  • Refresh Rotation: each /auth/refresh call issues a new pair and invalidates the old refresh token in Redis. If an old token is reused, the stored token is deleted (logging the user out), which protects against token theft.

9.2 Token Blacklisting

  • On logout, the access token is stored in Redis (token:<accessToken>) with the same expiry as the token's exp claim.
  • The userAuth middleware checks this blacklist before verifying the JWT.

9.3 Password Security

  • Passwords are hashed with bcrypt (salt rounds = 10).
  • Plain passwords are never stored or logged.

9.4 Code Execution Sandbox

  • All user code is sent to Judge0 CE, which runs submissions in isolated containers with CPU/RAM limits and no persistent filesystem. Network isolation depends on how your Judge0 instance is configured.
  • The application server never executes user-provided code directly.
  • Execution runs in BullMQ workers, not in the API process.

9.5 Input Validation

  • Backend: validator library and Zod schemas in controller logic (for example contest questions, email format).
  • Frontend: Zod schemas (loginSchema, signupSchema) validate data before submission.

9.6 CORS & Cookie Security

  • CORS allows http://localhost:5173 (dev) and the configured FRONTEND_URL in production.
  • Cookies are httpOnly: true. In production (NODE_ENV=production) they use secure: true and sameSite: 'none' (cross-site frontend/backend deployment). In development they use sameSite: 'lax'.

13. Key Algorithms & Business Logic

13.1 ELO Rating (Duels)

  • Base K-factor: 32.
  • Difficulty multiplier: Easy = 0.75, Medium = 1.0, Hard = 1.5 (weighted K).
  • Formula:
expected = 1 / (1 + 10^((loserRating - winnerRating) / 400))
newWinnerRating = winnerRating + K * (1 - expected)
newLoserRating  = loserRating  + K * (0 - expected)
  • File: utils/eloCalculator.js.

13.2 Contest Violation System (Anti-Cheat)

  • 3 strikes:
  • 1st violation → warning.
  • 2nd violation → strict warning.
  • 3rd violation → disqualified = true; rank removed from the leaderboard; the user cannot submit further.
  • Tracked in ContestRank and McqContestRank.
  • The frontend reports tab switches / minimize events via the reportViolation endpoint.

13.3 Submission Grading (Practice & Contest) ⭐

  • Uses the Judge0 batch API: all hidden test cases for a problem are submitted in one batch.
  • Practice submissions are graded in a BullMQ worker (see Section 3.3): 1. API creates the Submission with status = pending and enqueues a job. 2. Worker runs the batch against Judge0 and updates the submission. 3. Worker emits submission_result to user-{userId}. 4. Failed jobs are retried 3 times with exponential backoff; permanently failed jobs go to the dead-letter queue.
  • Statuses:
  • pending: queued or waiting for Judge0.
  • accepted: all test cases passed.
  • wrong: some test cases failed.

  • error: compilation/runtime error.

  • For contests, only the first accepted submission per problem counts towards the leaderboard (tie-breaker: earliest submission time).

13.4 Streak Calculation

  • Uses the userProblem collection (unique solved problems).
  • Aggregates distinct dates of accepted submissions.
  • Checks consecutive days from today backwards and stops at the first missing day.

13.5 Atomic Database Operations ⭐

Problem: concurrent requests (double-clicks, parallel joins) caused duplicate participants in contests because of a read-modify-write pattern.

Solution: replace it with MongoDB's atomic $addToSet:

// ❌ Old (race-prone):
contest.participants.push(userId);
await contest.save();

// ✅ New (atomic):
await Contest.findByIdAndUpdate(
  contest._id,
  { $addToSet: { participants: userId } },
  { new: true }
);

Why $addToSet?

  • The "does it exist?" check and the insert happen in one DB operation.
  • Uniqueness is enforced by the database, not by application code.
  • Parallel joins by the same user cannot create duplicates.

Applied to

  • Contestcontroller.js: registerForContest, joinContestByCode
  • Mcqcontestcontroller.js: the same two methods

14. Load Testing & Performance Benchmarks ⭐

CodeMaster was load tested with k6 to validate the async architecture under concurrency.

14.1 Test Configuration

  • Load: 100 concurrent virtual users (VUs)
  • Duration: 45 seconds (10 s ramp-up, 30 s hold, 5 s ramp-down)
  • Target: POST /code/submit/:problemId
  • Auth: 100 pre-registered JWT sessions (created by seed-users.js)

14.3 Key Insights

  1. The bottleneck was infrastructure, not application code. Sub-20 ms average latency on local infra shows the application itself is fast. The higher cloud numbers are consistent with network round-trips to a shared MongoDB Atlas M0 cluster and to serverless Upstash Redis.
  2. The queue absorbed the load in both environments. Both runs finished with a 0% failure rate even though infrastructure latency differed by more than an order of magnitude.
  3. The backend is stateless by design. With the Socket.io Redis Adapter and BullMQ, API instances can be added or removed without losing queued jobs; socket events published during a brief Redis disconnect may not be replayed (see Section 7.3).
